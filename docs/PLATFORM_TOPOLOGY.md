# 모멘터스 플랫폼 위상(topology) — "합칠까 나눌까"의 정답

> 2026-07-26. 사장님 질문: notes(플래너) 상세페이지를 만들다 보니 제품마다 메인·GNB·블로그를 또 만들어야 하나?
> 모멘터스로 다 흡수하는 게 맞나, 아니면 각자 사이트가 맞나? cue·mark·heyreci는?
> **한 줄 답: 사이트를 합치지 말고 '층'을 합친다. 허브+스포크는 이미 맞게 깔려 있고, 빠진 건 공용 층 4개다.**

## 1. 왜 흡수가 틀렸나 (스포크를 apex에 넣으면)

1. **책임 층이 다르다.** 거래 도메인엔 사업자 고지·환불·주문·CS가 붙는다. apex에 다 붙이면 apex가 법무·CS 페이지가 되고 "브랜드 얼굴"을 잃는다 — `APEX_STRATEGY.md` §1에 이미 원칙으로 박아둔 것.
2. **스택이 다르다.** apex=정적 생성기(gen_site.py) · notes=Workers+D1+R2 SPA · cue=Workers+KV+AI · mark=Astro 정적(작품 1,193건). 한 배포로 묶으면 서로를 인질로 잡는다(하나 고치려 전체 재배포·전체 회귀).
3. **데이터·세션이 다르다.** 주문·다운로드 토큰(notes) / 면접 세션(cue) / 인제스트 파이프라인(mark). 한 도메인 = 쿠키·권한 사고 표면 공유.
4. **격리 이득을 버린다.** 한 제품 장애·SEO 사고가 전 제품으로 번진다.

## 2. 왜 완전 분리도 틀렸나 (= 지금의 실제 결함)

- notes·cue·mark·heyreci가 **GNB·footer·법정·문의를 각자 손으로** 갖고 있다 = 같은 일 4벌.
- 검증된 사실(2026-07-26 실측):
  - `mark/src/layouts/Base.astro` — 모멘터스 링크 **0건**(귀환 갈고리 없음).
  - notes 푸터 — `by Momentus` 가 **링크가 아닌 텍스트**였다(오늘 링크로 교체).
  - notes — 자체 약관·개인정보·환불 페이지 **없음**(apex `/legal/*` 는 이미 있음).
- 즉 "두 번 세 번 일"의 실체는 사이트 개수가 아니라 **공용 층의 부재**다.

## 3. 확정 위상 — 허브 + 스포크

```
the-moment.us (apex = 허브: 브랜드·발견·신뢰·무료도구)   ← gen_site.py + data/products.json (지그, 이미 작동)
├── /products/<slug>   미끼 제품 = 여기서 완결(별도 도메인 불필요)
│     quickpang · insta-rank · youtube-rank · pinterest-grab · chatpage · her
├── /legal/*           약관·개인정보·환불 = 전 제품 정본 1벌
├── /log, /about        브랜드·사람 층
└── 스포크(거래 도메인 = 자기 앱·자기 결제·자기 CS)
      notes.the-moment.us   플래너 상점(D1·R2·Paddle)
      cue.the-moment.us     AI 모의면접
      mark.the-moment.us    로고(작품 1,193건 + 저널 74편)
      heyreci.com           AI 상품사진
```

**규칙 한 줄: 결제·계정·데이터가 있으면 스포크, 없으면 apex 안.** 새 서비스가 나오면 이 한 줄로 판단이 끝난다(더 고민하지 않는다).

## 4. 공용 층 4개 — 여기만 만들면 다시 일하지 않는다

| # | 층 | 무엇 | 왜 지금 |
|---|---|---|---|
| 1 | **껍데기(shell)** | `data/products.json` → 공용 `shell.js`+`shell.css` 1벌을 CDN/R2에 올리고 각 스포크가 `<script src>` 한 줄로 **상단 패밀리 바 + 공용 footer**(법정·문의·다른 제품)를 얻는다 | 새 제품 = products.json 한 줄 = **전 제품 footer 자동 갱신**. 지그를 apex 밖으로 배급하는 것 |
| 2 | **법정·문의** | apex `/legal/*` 만 정본, 스포크는 링크(제품 특수 조항만 추가) | notes에 약관·환불이 없다(전자상거래 위험). 4벌 쓰지 않는다 |
| 3 | **결제·주문·재다운로드** | planner-factory `payments.js`(Paddle)+주문·재발송이 유일한 완성 결제 층 → cue·heyreci가 결제 붙일 때 그대로 재사용(같은 계정·웹훅·전달 메일) | "결제 붙이는 일"을 세 번 하지 않는다 |
| 4 | **디자인 토큰(다크 포함)** | 라이트/다크 토큰 1벌 → 전 제품 상속 | 지금 apex·notes·mark 전부 라이트 온리. **다크는 제품마다 만들면 3벌**. 토큰 층에서 한 번 |

**콘텐츠(블로그)는 하나로.** 도메인마다 블로그를 새로 짜는 건 실익 대비 운영비 3배. mark의 저널 엔진(74편+RSS+검색)이 이미 검증됐으니 그 엔진을 공용으로 쓰고, 각 제품 페이지는 **태그 필터 뷰만 링크**한다.

## 5. 사례로 검증

- **37signals.com**(회사 허브) + basecamp.com · hey.com(각자 도메인·각자 결제) = 소수 인원 다작의 표준형. 우리 구조와 동일.
- **Panic** = 제품이 전부 앱이라 한 도메인 안에 다 넣음(거래 층이 스토어라 자기 결제가 없음) — 우리 미끼 제품(북마크릿·확장)이 apex 안에 있는 것과 같은 논리.
- **한 도메인 몰아넣기(네이버·카카오)** 는 **이미 청중이 있을 때만** 작동한다. `APEX_STRATEGY.md` §0-4의 "페이지는 수요의 하류"와 같은 얘기 — 청중 없는 지금 도메인을 합쳐도 권위는 생기지 않는다. 오히려 **같은 브랜드 껍데기가 4곳에서 반복 노출**되는 편이 유리하다(AEO의 다출처 반복언급과 같은 원리).
