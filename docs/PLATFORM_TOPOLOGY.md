## 2. 왜 흡수도 완전분리도 아닌가

**흡수(apex에 다 넣기)가 틀린 이유**
1. **책임 층이 다르다.** 거래 도메인엔 사업자 고지·환불·주문·CS가 붙는다. 다 흡수하면 apex가 법무·CS 페이지가 되고 브랜드 얼굴을 잃는다(`APEX_STRATEGY.md` §1 원칙).
2. **스택이 다르다.** apex=정적 생성기 / notes=Workers+D1+R2 SPA / cue=Workers+KV+AI / mark=Astro 정적(작품 1,193건) / kontext=로그인 앱. 한 배포로 묶으면 하나 고치려 전체를 재배포·재검증한다.
3. **데이터·세션이 다르다.** 주문·다운로드 토큰 / 면접 세션 / 인제스트 / 워크스페이스. 한 도메인 = 쿠키·권한 사고 표면 공유.
4. **격리 이득을 버린다.**

**완전분리가 틀린 이유 = 이번 세션의 실측 결함**
- `mark/src/layouts/Base.astro` — 모멘터스 링크 **0건**(귀환 갈고리 없음).
- notes 푸터 — `by Momentus`가 **링크도 아닌 텍스트**였다(2026-07-26 링크로 교체).
- notes — 자체 약관·개인정보·환불 **없음**(apex `/legal/*`엔 이미 있음).
- apex `products.json`·JSON-LD·법정 문서가 **폐기된 `planner.the-moment.us`** 를 가리켜 전 페이지가 301 한 홉을 태웠다(2026-07-26 정본화·재생성, 23파일 반영).

→ "두 번 세 번 일"의 실체는 **사이트 개수가 아니라 공용 층의 부재**다.

## 3. 껍데기 — 바는 2단, 연결은 스크립트 한 줄

```
┌──────────────────────────────────────────────────────────────────┐
│ MOMENTUS  플래너·마크·큐·컨텍스트 │ 무료 도구 │ 이야기 소개  헤이레시↗│ ← 1단(브랜드 바)
├──────────────────────────────────────────────────────────────────┤   전 사이트 동일. 절대 안 바뀜.
│ notes     제품  사용법  기업  이야기               [무료 받기]    │ ← 2단(제품 바)
└──────────────────────────────────────────────────────────────────┘   그 제품 것. 여기만 갈림.
```

**핵심: 1단은 안 바뀌고 2단만 갈린다.** 주소가 `notes.…`로 바뀌어도 1단이 그대로면 사용자는 "사이트를 나갔다"가 아니라 **"탭을 옮겼다"** 로 느낀다. 애플(`apple.com` 검은 바 + `/mac` 전용 2단 바)·어도비 Unified Shell·구글 앱 스위처·Atlassian 스위처가 전부 이 패턴.

**연결의 전부 = 각 제품 HTML에 한 줄**

```html
<script src="https://the-moment.us/shell.js" defer></script>
```

- `shell.js` + `products.json` 은 `momentus` 저장소에만 산다. 여기만 고치면 4개 사이트가 동시에 바뀐다.
- **저장소 합치기·서브모듈·패키지 배포 전부 불필요.** 코드는 계속 남남으로 두고 껍데기만 한 곳에서 그린다.

### ⚠️ 못박을 설계 규칙: 1단 바는 fail-open
> 공용 스크립트가 안 뜨면 **바만 사라지고 제품 사이트는 정상 판매**해야 한다. 2단 바는 각 제품 HTML에 자체 내장하고 공용에 의존시키지 않는다.

이 규칙이 있으면 껍데기를 공유해도 공유 실패점이 판매를 죽이지 않는다. ("하나 터지면 다른 것도 죽나?" → 각 제품이 별개 Cloudflare 워커/사이트라 격리됨. 2026-07-26 notes를 두 번 배포했으나 mark·cue·apex 무영향.)

## 4. 블로그 — 한 곳에 쌓고 태그로 갈라 본다

```
the-moment.us/이야기            ← 글이 사는 곳은 여기 한 곳뿐
   글마다 태그: [플래너] [마크] [큐] [컨텍스트] [무료 도구] [사람]

notes 2단 바 '이야기'  →  /이야기?태그=플래너
mark  2단 바 '이야기'  →  /이야기?태그=마크
1단 바 '이야기'        →  /이야기  (전체 — 섞여서 보임)
```

- **엔진 = mark의 저널 승격**(글 74편·RSS·검색이 이미 검증됨). 새로 짓지 않는다.
- 효과: 플래너 이야기 옆에 마크·큐 이야기, 그 옆에 사람 사는 이야기가 섞여 쌓여 방문자가 **"이 사람 플래너도 만들고 로고도 하고 면접도 하네"** 를 자동으로 알게 된다. 제품별로 쪼개면 이 인식이 절대 안 생긴다. (토스피드 = 토스·토스뱅크·토스증권·토스페이먼츠가 앱도 회사도 다른데 블로그는 하나)
- **경계 규칙: 마케팅·이야기 = 공용 블로그 / 제품 문서(Docs) = 그 제품 사이트.** kontext의 Docs는 kontext에, kontext GNB의 Blog는 공용 블로그 필터로.

## 5. 무료 도구 — 서브도메인이 아니라 경로 `/tools/`

**사례**: [Ahrefs `ahrefs.com/free-seo-tools`](https://ahrefs.com/free-seo-tools) · [HubSpot `hubspot.com/free-business-tools`](https://www.hubspot.com/free-business-tools) — 큰 회사도 무료 도구는 예외 없이 **본 도메인 경로**에 둔다.

**근거**: 구글은 서브도메인/서브폴더가 동등하다고 말하지만 실측은 **서브폴더가 더 빨리·잘 오른다**(본 도메인 권위·백링크 상속). 주제가 **완전히 다를 때만** 서브도메인. → 무료 도구는 **미끼**라 그 유입 권위가 본 도메인에 쌓여야 하므로 경로. 반대로 notes·cue·mark·kontext는 주제가 실제로 다르고 앱·결제·데이터가 붙으므로 서브도메인(= 그 예외에 정확히 해당).

**실행**: 지금 apex `/products/<slug>` 에 있는 6종(퀵팡·인스타 정렬·유튜브 정렬·핀터레스트·ChatPage·her)의 주소를 `/tools/<slug>` 로 바꾼다. 1단 바 라벨은 **`무료 도구`** 한 칸(개수가 계속 늘어 나란히 두면 바가 터진다).

## 6. 로그인 — 새로 만들지 않는다. kontext에 있는 걸 "옮긴다"

kontext는 이미 로그인이 붙어 있다(GitHub · Google · 이메일 3종, Supabase로 추정 — 미확인). **하는 일은 세 가지뿐이다.**

1. **현 상태 확인** — 어떤 인증을 쓰는지, 세션을 브라우저 어디에 저장하는지(localStorage vs 쿠키). 이 한 가지가 3번을 정한다.
2. **로그인 화면 주소만 `id.the-moment.us` 로** — 인증 서비스는 그대로 두고 로그인·회원가입 화면을 공용 주소에 세우고 리다이렉트 설정만 고친다.
3. **세션 쿠키를 `.the-moment.us` 로** — 그러면 **서브도메인끼리는 한 번 로그인으로 다 통한다.** (반대로 `heyreci.com`은 도메인이 달라 못 들어온다 → 별도로 빼신 판단이 기술적으로도 맞다.)

이후 notes·cue에 로그인이 필요해지면 하는 일은 **"로그인 만들기"가 아니라 손님(클라이언트) 등록 한 번**. 직접 짓지 말고 기성(Clerk·Auth0·Supabase Auth·Kinde) 프로젝트 1개에 앱들을 클라이언트로 등록한다.

### ⚠️ 지금 해야 하는 이유 = 사용자가 0명이라서
- **"쓰는 사람이 없어"가 반대로 지금 해야 하는 이유다.** 이관할 데이터가 없어 이 작업이 공짜다.
- 사용자가 쌓인 뒤 합치면 **중복 계정 병합 + 데이터 이관 + 전원 비밀번호 재설정 안내**가 붙는 대형 공사가 된다(Atlassian이 Trello 계정을 한참 따로 뒀던 이유).

### 지금 나머지 제품에 로그인을 붙이지 않는다
notes=이메일로 파일 전달이면 끝 / cue="회원가입 없음"이 셀링포인트 / mark=시안 열람. 로그인을 끼우면 전환율만 떨어진다. **필요할 때 붙이되, 붙일 자리를 지금 만들어 둔다.**

## 7. 결제 — "결제내역·환불이 답이 없다"의 답은 스마트스토어다

| 시점 | 무엇 | 왜 |
|---|---|---|
| **지금** (매출 0 → 첫 매출) | **네이버 스마트스토어로 전부** | 결제·환불·주문내역·CS를 **네이버가 대행** = 우리가 만들 게 0. notes·cue·mark 모두 단건이니 같은 방식으로 상품 등록. 초기 물량은 구매 확인 후 손으로 전달이 가장 빠르다 |
| **먼저 통일할 것** | **'다시 받기' 창구 한 개** | 결제보다 급한 건 산 사람이 파일을 다시 받는 경로. `planner-factory` 에 이미 완성(주문 저장·링크 재발송) → 공용으로 올려 cue·mark가 같이 쓴다. (2026-07-26 notes 푸터에 `/orders` 노출: 그전엔 결제완료 시트에서만 링크된 고아 경로였다) |
| **나중** (수수료 > 개발비) | **자체 결제 한 벌** | 국내=포트원/토스페이먼츠, 해외=Paddle(세금 자동). 한 창구에서 **구독(kontext) + 단건(나머지)** 동시 판매. `planner-factory` 의 Paddle 통합이 유일한 완성본이므로 그걸 승격 |

### 계정과 결제를 한 덩어리로 보지 않는다
**구독·이용량 = 계정 필요(kontext) / 단건 파일 판매 = 이메일로 충분(notes·cue·mark).** 억지로 통일하면 전환만 잃는다. "내 구매내역 한 곳에서 보기"가 필요해지는 날 §6에서 만든 자리에 붙인다.

## 8. 저장소 — 폴리레포 유지 + 공용 저장소 1개

- 제품들이 실제로 공유하는 코드가 **거의 없다**(플래너 엔진 Python / kontext 앱 / mark Astro 콘텐츠 / cue 워커). 모노레포의 이득(원자적 커밋·코드 공유)은 **코드를 공유할 때** 생기고, 비용(빌드·CI·컨텍스트 무게)은 **즉시** 생긴다.
- 정답 형태: **제품별 저장소(지금 그대로) + 공용 저장소 1개**(`shell.js`·디자인 토큰·결제 층·매니페스트). 1인 다작의 현실적 최적.

## 9. 새 서비스가 생기면 — 매니페스트 한 줄. 어드민 안 만든다

```
data/products.json 에 "recruit" 한 줄 추가  →  배포
   ├─ 1단 바에 '리크루트' 자동 등장 (notes·cue·mark·kontext 전부 동시)
   ├─ 블로그 태그 '리크루트' + /이야기?태그=리크루트 필터 자동
   ├─ 홈 카드 · 푸터 · 사이트맵 · JSON-LD 자동
   └─ 법정 문서의 서비스 목록 자동
```

방식 이름 = **매니페스트 구동(manifest-driven)**. apex IA 문서에 이미 "DB·헤드리스 SaaS·관리자 앱 만들지 않는다"로 원칙까지 박혀 있다.

**실증(2026-07-26)**: `products.json` 의 플래너 주소 한 줄을 고치고 `gen_site.py` 재생성 → **23개 파일이 한 번에** 맞춰졌다(URL 치환 28줄, 손으로 만진 HTML 0건).

## 10. 랜딩 페이지 — 허브가 스포크의 업데이트를 어떻게 아나

사장님 질문: 모멘터스 메인에 새 플래너·새 무료 도구·새 글·인스타/스레드/유튜브까지 올라오게 하고 싶은데, 제품들이 다 따로 노는데 apex가 그걸 어떻게 알고 관리하나.

### 답 ① — 모든 활동을 **한 스트림**으로 통일하고, 종류(kind)만 다르게 둔다
제품 출시·도구 추가·글·영상·소셜 포스트를 **전부 같은 타임라인의 항목**으로 본다. 랜딩은 그 스트림의 최신 N개를 종류별로 렌더할 뿐이다.

```
stream 항목 = { 날짜, kind, 제목, 링크, 썸네일, 태그(제품) }
   kind = release | tool | post | video | social

랜딩 = 이 스트림 하나를 여러 각도로 자른 것:
   "지금 새로 나온 것"  = 최신 3개 (kind 무관, 섞어서)
   "이야기"             = kind=post 최신 3편
   "미디어"             = kind=video|social 갤러리
   "제품 그리드"        = products.json (스트림 아님)
```

새 kind나 새 제품이 생겨도 **랜딩 구조는 안 바뀐다.** 이게 "두 번 일 안 하기"의 랜딩 버전.

### 답 ② — 수집은 **풀(pull)**. 제품에 배선하지 않는다
제품이 apex에 알리게 하면(푸시) 4곳에 배선이 생기고, 하나 실패하면 조용히 누락된다. 반대로 **apex가 빌드할 때 각 제품의 공개 피드를 읽어 온다**(풀). 제품이 할 일은 **정해진 파일 하나를 노출**하는 것뿐.

**이미 있는 것부터 재사용한다** (2026-07-26 실측):

| 제품 | 이미 있는 피드 | 상태 |
|---|---|---|
| mark | `/rss.xml` (308KB) · `/works.json` (1.1MB) | ✅ 그대로 씀 |
| notes | `/api/shop` (제품·가격 JSON) | ✅ 그대로 씀 |
| cue | 없음 | `/feed.json` 하나 추가 |
| kontext | 없음(Blog 있음) | `/feed.json` 하나 추가 |

**갱신 주기**: 하루 1회 cron 재빌드로 충분(이 머신은 이미 05:30에 `capabilities_scan` 을 돌린다). 배포 훅은 나중에.
**실패 처리**: 피드를 못 읽으면 **직전 캐시를 쓰고 조용히 넘어간다**(랜딩이 통째로 죽지 않게 — 껍데기와 같은 fail-open 원칙).

### 답 ③ — 소셜은 정직하게 반자동
- **유튜브 = 자동.** 채널 RSS가 공식으로 열려 있다(`youtube.com/feeds/videos.xml?channel_id=…`) → 풀로 처리.
- **인스타·스레드 = 수동 한 줄.** API 승인 문턱이 높고 스크래핑은 깨진다. **매니페스트에 링크+썸네일 한 줄 붙이는 게 오히려 싸다.** 여기에 이미 있는 수집 북마크릿(인스타 정렬·핀터레스트 추출)을 쓰면 링크 긁기가 반자동이 된다.
- 규칙: **자동화는 2개만(제품 피드 + 유튜브 RSS), 나머지는 손으로 한 줄.** 오버엔지니어링 방지선.

### 랜딩 세로 구성 (v2 원칙 = 방문자가 주인공)
1. **히어로** — 방문자 욕망 한 줄 + **무료 도구 즉시 체험**(북마크릿 드래그)
2. **지금 새로 나온 것** — 스트림 최신 3개(제품·도구·글·영상 섞어서)
3. **제품 그리드** — "하려는 일"별 정렬(돈 벌기 / 인스타·릴스 / 로고·브랜딩 / 나를 위한)
4. **이야기** 최신 3편
5. **미디어** — 유튜브(자동) + 인스타·스레드(수동 큐레이션)
6. **사람 층** → `/about` (도구로 감동시킨 다음에 등장)
7. **푸터** — 법정·문의 + 정량 문구(AEO 앵커)

### ⚠️ 신선도 함정 — "최근 업데이트"는 멈추면 사이트를 죽어 보이게 한다
- 규칙: 스트림 최신 항목이 **60일보다 오래되면 그 섹션을 자동으로 숨긴다.** 날짜는 최신 3개에만 노출.
- 이유: 빈 "최근 소식"이나 반년 전 날짜는 없는 것보다 나쁘다.

### "이거 오버엔지니어링 아닌가?" — 아니다. 단, 이유가 트래픽이 아니다
방문자가 0명이어도 **사장님 시간이 절약되므로 남는 장사**다(`APEX_STRATEGY.md` v2 §9의 1순위 논리와 동일). 대신 위 자동화 2개 상한선을 지켜서 "관리할 시스템"을 늘리지 않는다.
