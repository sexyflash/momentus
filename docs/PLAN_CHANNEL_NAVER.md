## 2. 경계 — PLAN_PAY_LAYER 규칙을 네이버로 확장

상위 규칙은 그대로다:

> **돈·주문·고객 신원이 닿으면 pay. 나머지는 서비스.**

네이버 채널은 그 규칙에 **예외가 아니라 특수 케이스**다 — 돈·주문이 닿지만 **원장을 우리가 소유할 수 없다.**

```
[① notes]  제품을 만든다. sku_id 를 발급한다.
   ⛔ 네이버 상품번호를 알 필요 없다.
        │  sku_id + 산출물(PDF·이미지·상세)
        ▼
[② 진열]   네이버에 상품을 만든다.
   등록 응답의 (originProductNo, optionId) 를 ③ 원장에 즉시 기록한다.
   ⛔ 파일을 만들지 않는다. 주문을 다루지 않는다.
        │  매핑 1행
        ▼
[③ slack-bot]  네이버 주문을 이행한다.
   ⛔ 상품을 만들지 않는다. 가격을 정하지 않는다.
   ⛔ 카탈로그를 손으로 채우지 않는다 — 등록이 채운다.
```

### 2-1. 왜 이행을 pay로 합치지 않는가

**네이버 주문의 원장은 네이버가 갖고 있고 우리가 소유할 수 없다.** pay로 복제하면 원장이 둘이 되고,
취소·환불이 네이버에서만 일어나는 순간 **반드시 어긋난다.** 어긋난 뒤에는 어느 쪽이 진실인지 판정할 방법이 없다.

대신 **카탈로그만 합친다** — `sku → 파일·가격·이행타입`은 pay가 원장이고 slack-bot은 읽는다.
그래야 파일이 바뀔 때 한 곳만 고친다.

| | 합칠 것 | 채널별로 둘 것 |
|---|---|---|
| 카탈로그 (sku→파일) | ✅ pay 원장, 나머지는 pull | |
| 주문·이행 | | ✅ 네이버=slack-bot / 자사몰=pay |

## 3. 접합면 = `sku_id`, 매핑 키 = `(originProductNo, optionId)`

### 3-1. 상품명·옵션명을 파싱하지 마라

SKU 매칭에 문자열 파싱을 쓰면 SKU가 늘 때 조용히 어긋나고, **어긋나면 고객이 다른 상품을 받는다.**
되돌릴 수 없으므로 이건 `slack-bot/CLAUDE.md` 룰 #1의 "비파괴 예외"에 해당하지 않는다.

매칭은 **번호 정확 일치**만 인정한다. 못 맞히면 틀린 걸 보내는 대신 **막고 사람을 부른다**.

### 3-2. `optionId`는 안정적이다 (실측)

옵션명을 바꿔 재저장해도 `optionId`가 유지되는 것을 확인했다.

```
수정 전: [(59522200561,'기본'), (59522200565,'플러스'), (59522200567,'프로')]
수정 후: [(59522200561,'기본'), (59522200565,'플러스'), (59522200567,'프로우')]  ← id 동일
```

→ **`(originProductNo, optionId)`를 매핑 키로 써도 안전하다.**

### 3-3. 판매자 관리코드는 지금 할 일이 아니다

`sellerManagementCode`(상품)·`sellerManagerCode`(옵션) 둘 다 저장된다. **그러나 20자 제한**이라
`all_in_one-dated-kr-2026-mon`(28자) 같은 sku_id를 그대로 못 넣는다.

optionId가 안정적이므로 **없어도 된다.** 나중에 값어치가 생기는 자리는 둘뿐이다 —
사람이 판매자센터에서 수동 등록했을 때의 대조 수단, 그리고 자사몰과의 공용 키.
그때 짧은 채널코드 체계(`AIO26MON-B` 형태)를 도입한다.

## 4. 네이버 상품 API 실측 규약

**전부 2026-08-06 실제 호출로 확인했다.** 벌크 스크립트를 짜는 사람이 여기서 시간을 아끼라고 남긴다.

| 항목 | 실측 |
|---|---|
| 상품 등록 `POST /v2/products` | ✅ **권한 있음** (403 아니라 400 필드요구) |
| 등록 응답 | `originProductNo` · `smartstoreChannelProductNo` · `originProduct`(옵션 id 포함) |
| 상품 삭제 `DELETE /v2/products/origin-products/{no}` | ✅ 동작 |
| **판매상태 지정** | ❌ **`statusType`이 무시된다. 무조건 `SALE`·노출 ON으로 생성** |
| **재고 0 등록** | ❌ 거부 — *"옵션가 0원·재고 1개 이상·사용여부 Y인 옵션이 최소 1개 필요"* |
| **판매시작일 미래** | ✅ **`statusType=WAIT`(판매대기)로 태어남** ← 벌크 안전장치 |
| `saleStartDate` 사용 시 | `saleEndDate` **필수** (없으면 400) |
| 날짜 포맷 | `2026-09-05` ❌ → `2026-09-05T12:00:00.000+09:00` ✅ |
| 옵션 관리코드 길이 | **20자 미만** |
| 판매상태 변경 전용 엔드포인트 | ❌ 없음(`change-status` 404). **전체수정 PUT**으로 한다 |
| 전체수정 PUT | GET 결과를 그대로 되돌려 넣고 바꿀 필드만 교체하면 안전 |

### 4-1. 주문 조회 쪽 제약 (2026-08-05 실측, `slack-bot/naver_commerce.py`)

| 항목 | 실측 |
|---|---|
| `last-changed-statuses` 조회 범위 | **24시간 초과 시 빈 응답/400** → 자동 분할 필요 |
| `lastChangedType` | **단일값만** → 상태별 union 호출 필요 |
| 디지털 상품 | PAYED 단계가 안 잡히고 PURCHASE_DECIDED로 점프하는 경우 있음 |
| **구매자 이메일** | ❌ **API가 주지 않는다.** 이름 + 휴대폰번호뿐 |
| 배송메시지 | `productOrder.shippingMemo` 로 전달됨 |

**구매자 이메일이 없다는 것이 전달 수단을 결정했다** — 카카오 알림톡(13원) + SMS 대체발송(18원).
상세: [`slack-bot/claudedocs/ALIMTALK_TEMPLATES.md`](../../slack-bot/claudedocs/ALIMTALK_TEMPLATES.md)

### 4-2. 상품 상세에 이미 한 약속 (지켜야 함)

플래너 상품 상세페이지에 이 문장이 이미 공지돼 있다:

> *"다른 연락처나 이메일로 수령을 원하신다면 **배송 메시지**에 적어주세요. 배송 메시지는 자동으로 처리돼요.
> 이때 기본 연락처 대신 메시지에 적힌 정보를 기준으로 발송됩니다."*

따라서 이행 로직은 `shippingMemo`를 **반드시** 읽어야 한다.
자유 텍스트에서 대체 수신처를 뽑는 판단은 **LLM이 한다** — regex로 번호를 긁으면
*"부재시 010-XXXX로 연락주세요"*(배송기사용)를 수신처로 오인해 **남의 번호로 상품 링크가 간다.**
애매하면 기본 연락처로 폴백한다(비파괴).

## 5. 벌크 등록 절차 — "팔릴 수 없는 상태로 태어나게"

등록 API가 `statusType`을 무시하고 무조건 판매중으로 만들기 때문에, 30종을 그냥 올리면
**매핑도 검수도 안 끝난 30종이 즉시 판매된다.** 주문이 들어오면 원장이 막아주지만(`blocked`),
고객은 결제하고 못 받는다.

```
① 판매시작일을 미래로 두고 등록      → WAIT(판매대기)로 태어난다
      saleStartDate = 한 달 뒤 (saleEndDate 도 같이)
              ↓
② 등록 응답의 (originProductNo, optionId) 를 그 자리에서 원장에 기록
      ← 여기가 "등록 = 매핑". 손 매핑이 사라지고 누락이 구조적으로 불가능해진다
              ↓
③ 파일 존재 검증 + 상세페이지 검수
              ↓
④ 준비 끝난 것만 판매시작일을 앞당겨 오픈
```

> ⚠️ `WAIT` 상태여도 `channelProductDisplayStatusType`은 `ON`으로 표시된다.
> 판매대기 상품이 스토어 앞단에 실제로 보이는지는 API로 판별되지 않는다(**미확인**).
> 확실히 하려면 ①에 "등록 직후 즉시 판매중지 PUT"을 겹친다 — 노출 창 **0.6초** 측정됨.

### 5-1. 등록 페이로드가 만족해야 하는 것

- 옵션 상품은 **옵션가 0원 + 재고 1개 이상 + 사용 Y** 인 옵션이 최소 1개
- 옵션가는 상품 기본가 범위 안
- 옵션 관리코드 20자 미만
- 날짜는 시각까지 포함한 ISO

## 6. 크롬 확장(②)의 위치가 바뀐다

`reci-smartstore-ext`는 **"법인·커머스 API 없이 개인이 지금 바로"** 를 전제로 만든 MVP다.
그 전제가 깨졌다 — 커머스 API로 상품 조회·등록·수정·삭제를 전부 확인했다.

| | 확장 | 등록 API |
|---|---|---|
| 사람 개입 | **상품마다 클릭** (저장 버튼을 안 누르는 설계) | 0 |
| 이미지 | ❌ 불가(브라우저 보안) | 가능 |
| 매핑 | 등록 후 별도로 찾아야 함 | **응답이 번호를 돌려줌** |

**벌크는 등록 API로 간다.** 확장은 버리지 말고 **예외 처리용 수동 도구**로 남긴다
(API가 막히는 카테고리, 일회성 수정 등).

## 7. 아직 확인 못 한 것 (정직하게)

| 항목 | 왜 미확인 | 언제 풀리나 |
|---|---|---|
| 주문 payload에 판매자 관리코드가 실리는지 | 실주문이 있어야 확인 가능 | 첫 실주문 때 자동으로 |
| `WAIT` 상품이 스토어 앞단에 보이는지 | API로 판별 불가 | 스토어 페이지 육안 확인 |
| 알림톡 템플릿 검수 통과 여부 | 카카오 심사 1~2 영업일 | `__ALIMTALK_WATCH__` 가 30분마다 감시 중 |

`slack-bot/store_fulfill.py`는 `optionCode`와 `productOption`을 **둘 다** 읽으므로
어느 쪽이 오든 동작한다. 첫 주문 때 실제 payload를 기록해 이 표를 갱신할 것.
