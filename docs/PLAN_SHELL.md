# PLAN_SHELL — 껍데기 공용화 실행 계획

> 2026-07-26. 위상 결정(`PLATFORM_TOPOLOGY.md`)을 실제로 착수하는 순서.
> **전제: 저장소를 모으지 않는다. 진행 중 작업을 멈추지 않는다.**

---

## 0. 이 계획의 전제 3개

1. **폴더를 모으지 않는다.** 공용화는 저장소를 합치는 일이 아니라, `momentus` 안에 **파일 2개**(`shell.js` · 확장된 `products.json`)를 만들고 각 제품이 **스크립트 한 줄**을 붙이는 일이다. `planner-factory`·`mark`·`cue`·`kontext`는 지금 위치·지금 구조 그대로 둔다.
2. **notes 작업을 멈추지 않는다.** 지금 유일하게 매출에 붙어 있는 라인이다. 껍데기 작업은 제품 **밖에서** 만들어 나중에 한 줄로 붙이므로 병행 가능하다.
3. **각 제품이 부담할 총량 = 스크립트 한 줄 + `feed.json` 한 개.** 제품당 30분 이하. 이 이상 제품 코드를 건드리는 설계면 잘못된 설계다.

### 현재 각 제품 상태 (2026-07-26)
| 제품 | 상태 | 이 계획에서 할 일 |
|---|---|---|
| notes | **활발히 작업 중**(상세·판매 준비) | 검증 1호. 스크립트 한 줄 |
| mark | 저널 자동 인제스트만 도는 유지 상태 | 스크립트 한 줄 + **저널 엔진 승격 원본 제공** |
| cue | 정지 | 스크립트 한 줄 + `feed.json` |
| kontext | **정지**(코드가 이 머신에 없음) | 나중. 재개하는 날 로그인까지 함께 |
| apex | 정적 생성기 가동 | 이 계획의 작업장 |

## 1. Phase 0 — 제품을 하나도 건드리지 않고 혼자 다 만든다 〔직렬 · 반나절~1일〕

작업 위치: `momentus` 저장소 **단독**. 이 단계가 끝나도 제품 사이트는 **아무 변화 없다**(위험 0).

- [ ] **0-1. `products.json` 스키마 확장** 〔15분〕 — 필드 추가: `bar_label`(1단 바 표기) · `kind`(`spoke`\|`tool`\|`external`) · `feed`(피드 URL) · `tag`(블로그 태그). 기존 필드는 건드리지 않는다.
- [ ] **0-2. `shell.js` 작성** 〔반나절〕 — `products.json`을 읽어 1단 바를 DOM에 주입. 요구사항:
  - **fail-open** — 스크립트가 죽거나 못 뜨면 바만 없고 제품 사이트는 정상.
  - 현재 페이지 도메인을 보고 **자기 항목을 활성 표시**(하드코딩 금지 — `nav-active-no-hardcode` 규칙).
  - CSS는 스코프를 좁혀 제품 스타일을 오염시키지 않는다(notes에서 상세 CSS가 스토어로 샜던 사고와 같은 종류).
  - 라이트/다크 토큰으로 색을 잡는다(나중 다크 작업이 여기서 끝나게).
- [ ] **0-3. apex를 첫 소비자로 붙여 검증** 〔30분〕 — apex 자기 페이지에 먼저 1단 바를 얹어 본다. 제품 리스크 없이 실물 확인.
- [ ] **0-4. 무료 도구 주소를 `/tools/<slug>`로** 〔1시간〕 — `gen_site.py`에서 6종 경로 변경 + 기존 `/products/<slug>`는 301. 1단 바 라벨은 `무료 도구` 한 칸.
- [ ] **0-5. apex 배포** — 여기서 밀린 `notes.the-moment.us` 정본화(23파일)도 같이 나간다.

**게이트**: apex에서 1단 바가 라이트/다크·모바일에서 깨지지 않고, 스크립트를 강제로 404 냈을 때 페이지가 정상이면 통과.

## 4. Phase 3 — 블로그 승격 〔Phase 2와 병렬 가능 · 1~2일〕

이 계획에서 **가장 큰 덩어리**. mark의 저널 엔진(글 74편·RSS·검색)을 apex로 올린다.

- [ ] **3-1.** mark 저널의 콘텐츠 모델·빌드 경로 파악 → apex로 이식할 최소 단위 결정.
- [ ] **3-2.** `the-moment.us/이야기` 세우기 + 태그 축을 `products.json`의 `tag`에 연결.
- [ ] **3-3.** `?태그=플래너` 필터 라우팅. 각 제품 2단 바의 `이야기`가 이 주소를 물게 한다.
- [ ] **3-4.** mark의 기존 저널 글 이관 여부 결정 — **권장: 이관하지 않고 mark에 남긴다.** 로고 작업물 문맥에 붙은 글이라 옮기면 맥락이 깨진다. 신규 글부터 공용에 쓴다.

## 5. Phase 4 — 랜딩 스트림 〔Phase 3 이후 · 1~2일〕

- [ ] **4-1. 제품 피드 규격 확정** — 이미 있는 것 재사용: mark `/rss.xml`·`/works.json`, notes `/api/shop`. cue·kontext는 `/feed.json` 신설.
- [ ] **4-2. 수집기** — apex 빌드 시 피드를 읽어 단일 스트림(`{날짜, kind, 제목, 링크, 썸네일, 태그}`)으로 합친다. **실패 시 직전 캐시 사용**(랜딩이 통째로 죽지 않게).
- [ ] **4-3. 유튜브 RSS** 연결(채널 피드), 인스타·스레드는 **수동 한 줄**. 자동화는 이 2개로 상한.
- [ ] **4-4. 랜딩 7단 구성** — 히어로(무료 도구 즉시 체험) → 지금 새로 나온 것(최신 3) → 제품 그리드 → 이야기 3편 → 미디어 → 사람 층 → 푸터.
- [ ] **4-5. 신선도 규칙** — 최신 항목이 60일 초과면 그 섹션 자동 숨김. 날짜는 최신 3개에만.
- [ ] **4-6. 하루 1회 cron 재빌드** 배선(이 머신은 이미 05:30 스캔이 돈다).

## 7. 직렬 / 병렬 지도

```
[전 구간 병렬] notes 판매 작업 ──────────────────────────────────▶ (멈추지 않음)

Phase 0 (apex 단독) ──▶ Phase 1 (notes 한 줄) ──┬──▶ Phase 2 (mark·cue 한 줄)
                                                └──▶ Phase 3 (블로그 승격) ──▶ Phase 4 (랜딩 스트림)
```

- **직렬이어야 하는 곳**: 0 → 1. `shell.js`가 실물에서 한 번은 검증돼야 나머지에 복붙할 수 있다.
- **병렬 가능**: 1 이후 2와 3. 블로그 승격은 껍데기와 독립이다.
- **절대 병렬로 두면 안 되는 것**: 제품 4개에 동시에 스크립트를 붙이는 것. 문제가 나면 원인이 4곳으로 흩어진다.
