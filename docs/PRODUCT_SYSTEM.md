# 제품을 어떻게 만들고, 묶고, 전시할 것인가 — 정본

> 2026-08-01. `PLATFORM_TOPOLOGY.md`(합칠까 나눌까)와 `INFORMATION_ARCHITECTURE.md`(뼈대) 위에 세운다.
> 저 둘이 **"어디에 두나"**를 답했다면, 이 문서는 **"어떻게 소개하고 전파하고 전시하나"**를 답한다.
> 새 제품을 만들 때마다 같은 고민을 처음부터 하지 않으려고 쓴다.

## 0. 30초 결론

| 질문 | 답 |
|---|---|
| tools 와 apps 를 어떻게 나누나 | **방문자가 다음에 할 행동**으로 나눈다. 지금 당장 씀=`/tools/` · 스토어로 감=`/apps/` · 다른 사이트로 감=`/products/` |
| 제품 리스트를 뭘로 묶나 | 종류(북마크릿·확장·앱)가 아니라 **"하려는 일"**. 종류는 부차 정보다 |
| 알툴즈 모델로 가는 게 맞나 | **아니다.** 그 모델은 유통 채널(다운로드 포털)과 함께 이미 수명이 끝났다 (§3) |
| 그럼 어떤 모델인가 | **많은 작은 것 + 각자 독립 착지 + 브랜드는 신뢰층**. 참조는 Sindre Sorhus·Rogue Amoeba·Panic (§4) |
| AI 시대의 다른 접근이 뭔가 | 전시를 **두 층**으로 짠다. 사람용 카드 + **에이전트가 읽는 카탈로그**. 유틸리티는 "~하는 법"의 답이라 이 전환에서 가장 유리한 품목이다 (§5) |
| 안 되는 제품은 | 접는다. 단 **URL은 절대 안 죽인다** — 설치본이 남아 있다 (§8) |

## 1. 축 3개 — 판단 규칙 한 줄

```
결제·계정·데이터가 우리 도메인에 있나?
├─ 있다 ─────────────────────▶ 스포크 (자기 서브도메인)   notes· mark· cue· kontext
└─ 없다 ─▶ apex 경로. 그 안에서 방문자가 다음에 하는 행동으로 갈린다
      ├─ 브라우저에서 지금 당장 쓴다 (설치 0 또는 1클릭) ─▶ /tools/<slug>/
      ├─ 스토어를 거쳐 설치한다 ───────────────────────▶ /apps/<slug>/
      └─ 다른 사이트로 넘어간다 (외부 제품) ───────────▶ /products/<slug>/
```

**왜 '우리가 뭘 만들었나'가 아니라 '방문자가 다음에 뭘 하나'인가.**
축이 갈리는 진짜 이유는 **CTA가 다르기 때문**이다. 셋은 사용자가 겪는 마찰이 완전히 다르다.

| 축 | CTA | 마찰 | 이탈 지점 |
|---|---|---|---|
| `/tools/` | 북마크바로 드래그 / 크롬에 추가 | 거의 0 | 없음 — 그래서 미끼로 쓴다 |
| `/apps/` | 스토어 열기 → 설치 → **권한 설정** | 높음 | **설치 후 설정에서 죽는다** |
| `/products/` | 다른 사이트로 이동 | 중간 | 브랜드가 끊기는 느낌 |

`/apps/`에만 **`setup` 페이지가 따로 있는 이유**가 여기 있다. 북마크릿은 드래그하면 끝이지만,
네이티브 앱은 설치 후 권한·설정에서 사용자가 사라진다. Flipper 실측이 그 증거다 —
삼성 One UI는 접근성 첫 화면에 앱이 **안 보이고** `설치된 앱`을 한 번 더 들어가야 한다.
앱이 그 화면으로 보내는 딥링크는 One UI가 무시한다. **그래서 웹 페이지가 그 구멍을 메운다.**

> 이건 문서가 아니라 **전환 장치**다. 앱 페이지를 만들 때 소개보다 `setup`이 먼저다.

## 2. 제품 리스트 — 묶는 축을 바꾼다

### 지금의 문제

`/tools/`가 **종류**로 묶여 있다(북마크릿 4 · 크롬 확장 2). 그런데 방문자는
"북마크릿을 찾으러" 오지 않는다. **"쿠팡 옵션 빨리 보는 법"을 찾으러** 온다.
종류는 우리 사정이지 그의 관심사가 아니다.

### 규칙

- **1급 정렬축 = "하려는 일".** 매니페스트의 `desire`(방문자 주어 욕망 한 줄)가 이미 그것이다.
  카드에서 제품명보다 `desire`가 먼저 읽혀야 한다.
- **종류·가격·플랫폼은 필터로 내린다.** 없애지는 않는다 — 결정 직전에 필요한 정보다.
- **한 줄 설명은 짧을수록 이긴다.** Sindre Sorhus는 63개 앱을 한 줄로 처리한다:
  "Quick notes, always available" / "Convert videos to high-quality GIFs".
  형용사를 빼고 **동사+목적어**로 끝내라.
- **제품이 늘어도 페이지 구조는 안 바뀐다.** 늘어나는 건 매니페스트의 행뿐이다.

### 리스트가 커질 때의 순서

제품 수에 따라 필요한 것이 달라진다. 미리 만들지 마라.

| 제품 수 | 필요한 것 |
|---|---|
| ~10 | 한 화면 그리드. 필터 불필요 |
| 10~25 | **"하려는 일" 필터** + 검색 |
| 25~ | 카테고리 인덱스 페이지 분리 + 최근/인기 축 추가 |

지금은 12개 언저리다. **필터를 넣을 때가 됐고, 카테고리 분리는 아직 이르다.**

## 3. 알툴즈 모델을 따라가면 안 되는 이유

형이 짚은 대로 지금 모양은 알툴즈(ESTsoft)와 닮았다 — **무료 유틸을 여러 개 뿌려 브랜드를
알리고, 그 신뢰로 유료 제품을 판다.** 구조는 같다. 그런데 **그 모델은 이미 한 번 죽었다.**

**실측**: ALTools는 일본에서 2016년경 窓の杜 등재가 끊겼고 ALSong 등 주요 제품이 공개를 종료했다.
제품이 나빠져서가 아니라 **유통 채널이 사라져서**다. 2000년대 유틸 묶음의 유통은
다운로드 포털(Vector·窓の杜·심파일)이었는데, 그 층 자체가 브라우저·앱스토어·클라우드로 대체됐다.

**교훈: 묶음(suite) 브랜드는 유통 채널이 살아 있을 때만 작동한다.**
채널이 죽으면 묶음이 통째로 같이 죽는다. 개별 제품이 각자 발견되고 있었다면 살아남았을 것들도 같이 죽는다.

### 그래서 지키는 규칙

- **묶음에 유통을 걸지 마라.** 각 제품은 **자기 힘으로 발견되어야** 한다
  (검색·AI 답변·스토어·커뮤니티에서 각자 착지).
- **브랜드는 유통 수단이 아니라 신뢰층이다.** 1단 바가 하는 일이 정확히 그것이다 —
  "이거 만든 데가 저것도 만들었네"를 알려줄 뿐, 그것으로 트래픽을 만들지는 않는다.
- **"모멘터스 툴 모음 설치" 같은 묶음 배포를 만들지 마라.** 그게 알툴즈가 죽은 방식이다.

## 4. 참조할 모델 — 우리 크기에 맞는 것

| 모델 | 무엇을 훔칠까 | 주의 |
|---|---|---|
| **Sindre Sorhus** (1인, 앱 63개) | **가장 가까운 모델.** 그리드 + 카테고리 필터(무료/유료/Mac/메뉴바…), 앱마다 전용 페이지, 극단적으로 짧은 한 줄 | 개인 신뢰가 자산이라 `/about`이 진짜로 일한다 |
| **Rogue Amoeba** (맥 오디오 유틸 소수) | 제품 수를 늘리지 않고 **깊이로 승부**. 각 제품이 카테고리 1등 | 우리는 아직 폭이 필요한 단계 |
| **Panic** (Transmit·Nova·Playdate) | **장인 브랜드**. 제품이 달라도 만듦새 톤이 하나 | 디자인 투자 여력이 전제 |
| **37signals** (Basecamp·HEY·ONCE) | 제품마다 **선언문**을 준다. "왜 이렇게 만들었나"가 곧 마케팅 | 논쟁적 톤은 1인에게 리스크 |
| **알툴즈** | 무료→유료 깔때기 구조 자체 | **유통을 묶음에 걸었다가 채널과 함께 죽었다** (§3) |

**결론: Sindre Sorhus의 리스트 운영 + Panic의 만듦새 톤 + 37signals의 "왜"를,
알툴즈의 묶음 유통 없이** 가져온다.

## 5. AI 시대의 다른 접근 — 전시를 두 층으로

여기가 형이 물은 **"참신한 방법"**의 답이다. 디자인 얘기가 아니라 **유통 구조** 얘기다.

### 무엇이 바뀌었나

전통 경로는 `사람이 검색 → 랜딩 → 설치`였다. 2026년 현실은 다르다.

- **문서 사이트 트래픽의 절반 가까이가 사람이 아니라 에이전트**다 (Cursor·Claude Code·ChatGPT 등).
- 에이전트는 **검색 결과나 앱스토어로 발견하지 않는다.** CLI·MCP 서버·**기계가 읽는 문서**로 발견한다.
- 그래서 새 규율 이름이 생겼다 — AEO/GEO(생성엔진 최적화). 핵심은 **MCP 서버를 가진 쪽을 에이전트가 끌어다 쓴다**는 것.

### 왜 이게 하필 우리에게 유리한가

**유틸리티는 본질적으로 "~하는 법"이라는 질문의 답**이다.
사람이 예전엔 구글에 "쿠팡 옵션 한 번에 보는 법"을 물었고, 지금은 챗봇에 묻는다.
그 답변 안에 우리 도구가 후보로 들어가는 것 — **그게 새 유통이다.**

그리고 **대기업이 아니라서 오히려 유리하다.** 이런 긴 꼬리 질문은 큰 회사가 다루지 않는다.
앤트로픽·OpenAI 같은 곳은 반대 방향으로 간다 — 여러 제품을 **하나의 허브(Claude)로 수렴**시키고
MCP 같은 **표준을 깔아 남들이 붙게** 만든다. 우리는 표준을 깔 위치가 아니라 **그 표준 위에 얹히는 쪽**이다.
그 비대칭이 기회다. 그들이 만든 배급망에 무임승차한다.

### 실행 — 두 층

**층 1 (사람) — 지금 하고 있는 것.** 카드·상세·이야기·1단 바. 계속 간다.

**층 2 (에이전트) — 같은 매니페스트에서 뽑는다.** 새로 쓰는 게 아니라 *같은 소스의 다른 출력*이다.

| 무엇 | 왜 | 상태 |
|---|---|---|
| `/llms.txt` | 사이트 전체를 에이전트가 한 장으로 파악 | 미구현 |
| 제품별 **원자 답변 40~60단어** | 에이전트가 그대로 인용할 단위. `IA §D`에 이미 원칙으로 있다 | 부분 |
| 구조화 카탈로그(JSON) | 에이전트가 목록을 기계적으로 읽음 | `products.json`을 공개 엔드포인트로 열면 끝 |
| **MCP 서버** | 에이전트가 *추천*을 넘어 *실행*까지 | `momentus-studio` MCP가 이미 있다 — 확장 여지 |

### 층 2를 위한 페이지 작성 규칙

- 각 제품 페이지 맨 위에 **질문형 헤딩 + 40~60단어 답**을 둔다.
  사람이 챗봇에 던지는 문장 그대로를 헤딩으로 쓴다.
- **정량·날짜를 박는다.** "사용자 4,000명 · 별점 4.8 · v2.9.7(2026-08)".
  에이전트는 근거가 붙은 문장을 인용한다. 근거 없는 형용사는 버려진다.
- **북마크릿·확장은 에이전트가 실행할 수 없다.** 대신 **에이전트가 사람에게 건네줄 수 있는 형태**를 갖춘다 —
  정확한 URL + 무엇을 하는지 한 문단 + 설치 한 줄. 이게 층 2의 최소 단위다.
- 깨끗한 시맨틱 HTML. 이미지 안에 글자를 넣지 마라 — 에이전트가 못 읽는다.

> ⚠️ **과투자 금지선.** llms.txt에 올인하거나 대형 스키마를 짜지 마라.
> `IA §D`에 이미 결론이 있다 — **AEO의 진짜 동력은 페이지 밖 다출처 반복언급**이다.
> 사이트는 그것들이 가리키는 앵커일 뿐이다.

## 6. 제품 페이지 한 장의 표준 구조

### `/tools/<slug>/` — 무료 도구

1. 욕망 한 줄(`desire`) → 2. **즉시 실행 CTA**(드래그/스토어) → 3. 무엇이 되는가 3개
→ 4. 스펙 표 → 5. 쓰는 법 3단계 → 6. FAQ(질문형) → 7. 귀환 갈고리

### `/apps/<slug>/` — 스토어 앱 (3장 세트)

| 페이지 | 목적 | 필수 |
|---|---|---|
| `/apps/<slug>/` | 소개·다운로드 | 상태 배지(비공개 테스트/출시). **없는 스토어 버튼을 만들지 마라** |
| `/apps/<slug>/setup/` | **설치 후 이탈 방지** | 기기별 분기 탭 · 단계별 스크린샷 · 트러블슈팅 |
| `/apps/<slug>/support/` | 문의·구독/환불 | 이메일 + 법정 문서 링크 |

### `/products/<slug>/` — 외부 스포크

소개 + **밖으로 보내는 CTA 하나**. 우리 도메인에서 결제를 흉내 내지 마라.

### 전 페이지 공통 금지

- ❌ 검증 안 된 수치·형용사 (`CLAUDE.md` 룰 #5). 별점·사용자수는 **스토어 실측값**만.
- ❌ 기기·환경을 실측 없이 단정. 모르면 **"확인하지 못했습니다"**라고 쓴다.
  (2026-08-01: 순정 안드로이드 접근성 경로를 단정해 적었다가 정정)
- ❌ 법정 문서를 제품마다 새로 만들기. `/legal/*` 하나를 전부가 공유한다.

## 7. 앱에 박는 주소는 `/l/<키>` — 절대 실제 경로를 박지 마라

앱은 스토어에 올라가면 **URL을 못 고친다**(재빌드+재심사). 사이트 경로는 계속 바뀐다.

```
앱에 박는 것 (불변)          실제 페이지 (자유롭게 이동)
/l/flipper/setup  ──302──▶   /apps/flipper/setup/
```

- 매핑 원본 = `data/products.json` 의 `links.map`. **한 줄 고치면 끝. 앱 재빌드 0.**
- 처리 = `workers/link-redirect/`. **`_redirects`에 두지 마라** —
  개별 규칙을 catch-all보다 먼저 뒀는데도 catch-all이 전부 삼켰다(2026-08-01 실측).
- **반드시 302 + `no-store`.** 301은 목적지가 영구 캐시돼 나중에 못 바꾼다.
- 없는 키는 홈으로 302. **404를 내지 않는다** — 앱 웹뷰의 404가 최악이다.
- 법정 문서 `/legal/privacy/`·`/legal/terms/`는 이미 앱과 스토어에 박혀 있어 **영구 고정 주소**다. 옮기지 마라.

## 8. 접을 때 — 죽이되 URL은 남긴다

여러 개를 만드는 전략의 필연은 **안 되는 걸 접는 것**이다. 접는 걸 미루면 목록이 썩는다.

- 매니페스트에 `status`를 둔다: `live` · `closed-test` · `sunset`.
- **`sunset`은 리스트에서 내리되 페이지와 URL은 남긴다.** 이미 설치한 사람이 있고,
  스토어 등재정보가 그 주소를 가리키고 있다.
- 접는 이유를 한 줄 쓴다. 그 자체가 `이야기` 소재다(37signals가 하는 것).
- **`/l/` 키는 접어도 살려 둔다.** 목적지만 안내 페이지로 바꾼다.
